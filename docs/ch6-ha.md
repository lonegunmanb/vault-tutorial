# 6.6 集群高可用模式（HA）的设计哲学及其数据一致性保障

> **核心结论**：Vault 的高可用（High Availability，简称 HA）模式通过同时运行多台 Vault 服务器、并依赖底层数据存储（data store）的分布式锁来选出唯一的"活跃节点（active node）"，其余节点全部进入"待命节点（standby node）"状态。HA 模式的目标是**避免单台 Vault 实例宕机导致服务整体不可用**，而**不是**为了让多台节点同时分担读写压力。本节按"HA 模式的本质 → 节点间通信 → 客户端请求被处理的两条路径（请求转发与客户端重定向） → 与之相关的关键配置项 → 受支持的存储后端"的顺序，把 HA 概念里学员必须分清的几对易混淆术语彻底拉直。
>
> 本节是 6.4 节"Integrated Storage（Raft）协议与自动化运维"的并列章节。6.4 节聚焦"Raft 这一种 HA 存储后端内部如何保证数据复制"，本节则上升一层，聚焦"任何 HA 存储后端之上 Vault 集群整体如何对外提供单一一致的服务视图"。

---

## 1. HA 模式的本质：用数据存储中的分布式锁选出唯一活跃节点

Vault 通过**多服务器模式（multi-server mode）**支持高可用。该模式通过同时运行多台 Vault 服务器来防御宕机；只要所选用的数据存储（data store）支持 HA，HA 模式即被自动启用，无需额外开关。

判断当前所选数据存储是否支持 HA 的方法是：启动 Vault 服务器，观察启动日志里数据存储信息旁是否打印有 `(HA available)`；同样的信息也可以在官方 Configuration 文档页查到。

为了实现高可用，**所有 Vault 节点会争抢数据存储中的一把锁；抢到锁的那一台成为活跃节点（active node），其余全部进入待命节点（standby node）状态**。当待命节点收到客户端请求时，它会**根据当前配置与集群状态**采取两种处理方式之一：把请求转发给活跃节点（request forwarding），或者把客户端重定向到活跃节点（client redirection）。本节后面两节将分别展开这两种路径。

> **必须澄清的常见误解**：HA 模式**不能提升 Vault 的吞吐能力**。Vault 的性能瓶颈通常在于其下方的数据存储本身，而不是 Vault 的核心进程；因此若希望在使用 Consul 作为存储后端时为 Vault 扩容，惯常做法是**先扩容 Consul，而不是 Vault**。这一点对运维容量规划至关重要：HA 副本只用于"挡住宕机"，并非用于"扛住更高 QPS"。

某些存储后端可以同时存放 Vault 的业务数据与 HA 锁；但 Vault 也支持"数据 / HA 分离"的部署形态——通过在配置文件中**同时**声明 `storage` 和 `ha_storage` 两个块、并指向不同的后端。例如：使用 Consul 作为 `ha_storage` 来管理锁，同时使用 Amazon S3 作为 `storage` 存放其余持久化数据。

![HA 模式选主示意：多台 Vault 节点竞争数据存储中同一把分布式锁，抢到锁的那台成为唯一对外写入的活跃节点，其余全部转为待命，等到活跃节点失效时通过释放锁触发新一轮竞选](/images/ch6-ha/ha-leader-election.png)

## 2. 节点之间如何通信：先通过加密存储"广播"，必要时再建 mTLS 直连

请求转发与客户端重定向这两种处理方式都依赖**活跃节点向其它节点广播自身的位置信息**。这种"广播"**不走网络直连，而是写入 Vault 的加密存储中**：活跃节点写、已解封的待命节点读。

对于客户端重定向路径，节点之间的通信仅限于上述这种"通过共享的加密存储交换状态"，**不存在任何节点间直接的网络通信**。

![节点广播自身地址的方式：活跃节点把自己的可达地址写入加密存储这个共用"留言板"，待命节点定期读取以获知当前的活跃节点是谁](/images/ch6-ha/ha-state-via-storage.png)

对于请求转发路径，节点之间则**必须**直接通信。为了安全地完成这一通信，活跃节点会**额外**通过加密存储广播一对**新生成的 ECDSA-P521 私钥**与一张**新生成的、同时具备 client / server 用途的自签名证书**。每个待命节点拿到这对私钥与证书后，会通过活跃节点广播的 cluster 地址（cluster address）向其打开一条**双向认证（mutually-authenticated）的 TLS 1.2 连接**。当客户端请求到达待命节点后，待命节点把请求序列化、通过这条 TLS 通道发送至活跃节点；活跃节点处理完后将响应原路返回，待命节点再回送给客户端。

![请求转发的双向 mTLS 通道：活跃节点为节点间通信单独生成一把短期密钥与自签名证书并通过加密存储分发，待命节点用其建立 TLS 1.2 双向认证通道，把客户端请求"打包快递"过去再把响应原路带回](/images/ch6-ha/ha-request-forwarding-mtls.png)

## 3. 请求转发：默认行为与"强制回退"开关

请求转发（request forwarding）功能从 Vault 0.6.2 起**默认启用**。这意味着只要客户端连到了一个待命节点，请求都会被自动转发给活跃节点处理，对客户端而言完全透明。

如果客户端出于特定原因希望强制使用更老的"客户端重定向"行为，可以在请求 HTTP 头中设置 `X-Vault-No-Request-Forwarding` 为任意非空值；待命节点见到该请求头后会跳过转发，直接走重定向路径返回 `307` 状态码。

> 实务建议：绝大多数应用都应保留默认的请求转发行为，因为重定向会让客户端额外多发一次跨节点的 HTTP 请求；只有在排查"待命节点是否真的认为某台节点是 active"这类问题时，才会临时将该 header 打开作为诊断手段。

## 4. 客户端重定向：何时触发、为何 `api_addr` 必须配置

当请求转发功能被关闭、或转发过程出错、或请求里显式带了 `X-Vault-No-Request-Forwarding` header 时，待命节点会以 HTTP **`307` 状态码**把客户端重定向到**活跃节点的"重定向地址"**。

由于这种回退路径在任何 HA 部署中都可能被触发，因此**所有 HA 部署都必须能让待命节点说出"活跃节点的对外可达地址是什么"**。某些 HA 数据存储驱动可以自动探测该地址，但更常见的做法是通过配置文件的顶层 `api_addr` 显式设置；同样可以使用环境变量 `VAULT_API_ADDR` 覆盖文件中的值，且环境变量优先级更高。

`api_addr` 的取值**必须是一个完整的 URL**（包含 `http` / `https` 协议头，而不能只是 IP+端口）。它具体应当指向哪个地址，取决于客户端访问 Vault 的方式——下面分两种最常见的部署形态展开。

### 4.1 客户端可直接访问每台 Vault：`api_addr` 指向节点自身

当客户端可以直接访问每台 Vault 节点时，每个节点的 `api_addr` 都应当**指向该节点自己**的对外地址。例如有两台 Vault 节点：

- `A`，对外地址为 `https://a.vault.mycompany.com:8200`
- `B`，对外地址为 `https://b.vault.mycompany.com:8200`

那么节点 `A` 的 `api_addr` 应当配置为 `https://a.vault.mycompany.com:8200`，节点 `B` 的 `api_addr` 应当配置为 `https://b.vault.mycompany.com:8200`。这样配置之后，当 `A` 是活跃节点而客户端不慎连到了 `B`，`B` 会把客户端重定向回 `A` 的 `api_addr`；反之亦然。

### 4.2 仅能通过负载均衡器访问 Vault：所有节点的 `api_addr` 都填负载均衡器地址

某些场景下，客户端把"负载均衡器"作为接入入口，但实际上又**有能力直连每台 Vault 节点**——这种情况应按 4.1 节的方式配置，因为对重定向而言客户端是"直连"的。

但若客户端**只能**通过负载均衡器访问 Vault，则每个节点的 `api_addr` 都应当填同一个值——即**负载均衡器的地址**。此时被重定向到待命节点的客户端会被 `307` 转回负载均衡器；这要求负载均衡器自身的配置在每一刻都准确知道当前活跃节点是谁，否则就会产生重定向死循环。**官方因此明确不推荐这种部署形态**，能避免就尽量避免。

![负载均衡器后部署 Vault 时的重定向死循环陷阱：客户端 → LB → 待命节点 → 307 重定向回 LB → LB 再次随机挑一台→ 又落到待命节点……如果 LB 自身没有"知道当前活跃节点"的能力，这条循环将无法收敛](/images/ch6-ha/ha-lb-redirect-loop.png)

## 5. cluster port 与 `cluster_addr`：节点间通信专用的"第二条腿"

Vault 的每个 `listener` 块都包含一个 `address` 字段——监听**面向客户端 API 请求**的入口；与之并列，每个 `listener` 块还可以再设一个 `cluster_address` 字段——监听**面向节点间集群请求**的入口。如果未显式设置 `cluster_address`，Vault 将自动取与 `address` 相同的 IP，并把端口取为 `address` 的端口加 1（因此默认的 cluster 端口是 `8201`）。

需要特别注意的是：**只有活跃节点会真正打开 cluster listener**——当一台节点变为活跃时，它启动 cluster listener；当它退回待命时，它又会停止 cluster listener。

与 `api_addr` 类似，每台节点还需要在配置文件的顶层声明 `cluster_addr`，告知集群中的其它节点"如果我成为活跃节点，请通过哪个地址跟我建立节点间 TLS 连接"。该地址应当指向本节点 listener 中 `cluster_address` 所对应的某个真实可达的主机名或 IP（含端口）。**节点间通信永远走 HTTPS，因此该地址将被 Vault 强制按 `https` 处理。** 该值同样可以使用环境变量 `VAULT_CLUSTER_ADDR` 覆盖配置文件，环境变量优先级更高。

> **`api_addr` 与 `cluster_addr` 的对照口诀**：`api_addr` 是"告诉客户端从哪儿找到当前活跃节点"，使用 API 端口（默认 8200）；`cluster_addr` 是"告诉其它 Vault 节点从哪儿找到当前活跃节点"，使用 cluster 端口（默认 8201）。两者一定要分别配置，混淆后果之一就是请求转发链路无法建立、客户端最终只能依赖 307 重定向。

## 6. 受支持的 HA 数据存储后端：官方推荐 Integrated Storage

目前支持 HA 模式的存储后端包括 **Consul**、**ZooKeeper** 与 **etcd**——但这一名单会随版本迭代发生变化，最准确的清单始终应以官方 Configuration 页为准。

HashiCorp 对**新部署**的官方推荐是 **Vault Integrated Storage**，将其作为默认 HA 后端；**Consul Storage Backend** 同样仍是受支持选项，并且被许多生产部署沿用至今。两者之间如何选型，可参考官方 "Integrated Storage vs Consul as Vault storage" 比较表。

> 与本课程的衔接：本节只在概念层介绍 HA 后端的存在与官方推荐；具体到 "Raft 怎么复制日志、Autopilot 如何接管节点生命周期、Recovery Mode 如何抢救一个 quorum 永久丢失的集群" 这些更深的运维细节，已在 6.4 节"Integrated Storage（Raft）"中系统展开。本课程**不深入** Consul / ZooKeeper / etcd 这三种第三方后端的部署细节——它们在开源版本课程范围之外更多属于第三方系统的运维知识。

## 7. 章节小结：HA 模式留给学员的四张"心智地图"

1. **HA 是为了挡宕机、不是为了扛 QPS**：抢锁选主、单一 active 接收所有写入；扩容应往数据存储后端方向考虑，而非简单堆 Vault 节点。
2. **请求会被自动转发，但仍须为重定向兜底**：`api_addr` 是任何 HA 部署的硬性配置项；`X-Vault-No-Request-Forwarding` 仅作为诊断开关存在。
3. **节点间通信有两条独立路径**：通过加密存储"广播状态"（任何 HA 部署都用），以及通过 cluster port 上的双向 TLS"直连转发"（启用请求转发时才用）。
4. **`api_addr` 与 `cluster_addr` 不是同一回事**：前者面向客户端、走 8200；后者面向其它 Vault 节点、走 8201；两者都需要写在配置文件顶层并保证可达。

掌握以上四点，再结合 6.4 节关于 Raft / Autopilot / Recovery Mode 的具体机制，学员就具备了独立排障一个 HA Vault 集群上"客户端连不上 / 转发失败 / 选主异常"这三类典型问题的能力基础。

## 8. 互动实验

本节配套了一个 Killercoda 实验，学员将在单台 Killercoda 主机上以端口区分启动一个 3 节点 Vault Raft 集群（每个节点都把 `api_addr` 配置为指向自身），通过原生 `curl` 与 `sys/leader` API 把上述四张"心智地图"逐一变成可观察的现象。完成下列练习：

1. 启动并初始化 3 节点集群，使用 `sys/leader` 区分 active 与 standby 节点；
2. 不带任何额外请求头向 standby 发起 KV 读取，从 CLI 与 `curl -i` 两个角度确认 standby 默认就把请求**透明转发**到 active，客户端只看到 `200 OK`；
3. 在同一请求上加 `X-Vault-No-Request-Forwarding: 1` 头，复现底层的 `307` 重定向行为，并对比 `Location` 头与 `sys/leader.leader_address`，确认重定向目标正是 active 节点的 `api_addr`；
4. kill 掉当前 leader 触发 Raft 重新选举，等新 leader 出现后再次执行步骤 2 与步骤 3，验证转发路径与重定向路径都自动跟随新 leader 迁移、数据完整保留。
